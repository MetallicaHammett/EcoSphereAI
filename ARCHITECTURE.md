### Request Flow

1. **User Interaction**: User interacts with React frontend (dashboard, forms, visualizations)
2. **API Request**: Frontend sends HTTP requests to Django REST API at `/api/v1/`
3. **Authentication**: Django validates JWT tokens and checks permissions
4. **Business Logic**: Django processes request, interacts with services and models
5. **Database Operations**: ORM queries PostgreSQL/PostGIS for data persistence
6. **AI Processing**: For analytics/recommendations, calls AI microservices or internal ML modules
7. **Response**: Django serializes data and returns JSON response to frontend
8. **Rendering**: Frontend updates UI with received data

### Frontend ↔ Backend ↔ Database ↔ AI Flow

**Data Flow (Read)**:
Frontend → `/api/v1/endpoint/` → Django View → Service Layer → Repository/Manager → Database → Serialized Response → Frontend

**Data Flow (Write)**:
Frontend → `/api/v1/endpoint/` (POST/PUT/PATCH) → Django View → Validators → Service Layer → Database Transaction → Serialized Response → Frontend

**AI Flow**:
Frontend → `/api/v1/ai/endpoint/` → Django View → AI Service → ML Model/LLM → Processed Result → Database Cache → Response

## 4. Django App Responsibilities

### accounts
- **Purpose**: User authentication, authorization, profiles, and role management
- **Models**: User (extended), Profile, Role, Permission, UserSession
- **APIs**: Register, Login, Logout, Password Reset, Profile CRUD, Role Assignment
- **Services**: AuthenticationService, JWTService, PasswordService, EmailService
- **Permissions**: IsAuthenticated, IsAdmin, IsStaff, IsStudent, Role-based permissions
- **Dependencies**: Django contrib.auth, djangorestframework-simplejwt, django-allauth

### core
- **Purpose**: System-wide settings, configurations, and utility functions
- **Models**: SystemConfiguration, GlobalSettings, NotificationTemplate, Currency, Unit
- **APIs**: Get/Update system settings, Health check, Version info
- **Services**: ConfigurationService, CacheService, LocalizationService
- **Permissions**: IsAdmin or SystemOwner only for most operations
- **Dependencies**: Django core utilities

### campus
- **Purpose**: Manage university/college campus entities and hierarchy
- **Models**: Institution, Campus, Building, Floor, Room, Zone
- **APIs**: CRUD for all campus entities, Hierarchy navigation, Search/filter
- **Services**: CampusService, HierarchyService, GeolocationService
- **Permissions**: Based on user's institution/campus association
- **Dependencies**: django-contrib-gis (for PostGIS), geopy

### resources
- **Purpose**: Track consumption and management of utilities/resources
- **Models**: ResourceType, ResourceMeter, ResourceConsumption, UtilityBill, Supplier
- **APIs**: Resource consumption tracking, Bill generation, Supplier management
- **Services**: ConsumptionCalculationService, BillingService, SupplierService
- **Permissions**: Resource viewers vs editors based on role
- **Dependencies**: None beyond Django core

### carbon
- **Purpose**: Carbon footprint calculation, tracking, and reporting
- **Models**: EmissionFactor, CarbonEmission, OffsetProject, CarbonCredit, ReductionTarget
- **APIs**: Calculate emissions, View carbon footprint, Manage offsets, Set targets
- **Services**: CarbonCalculationService (core engine), OffsetService, ReportingService
- **Permissions**: View based on association, Edit based on role
- **Dependencies**: External emissions factor databases, calculation libraries

### sensors
- **Purpose**: IoT device management and real-time sensor data handling
- **Models**: SensorType, Sensor, SensorReading, SensorAlert, Gateway, CalibrationRecord
- **APIs**: Sensor CRUD, Real-time data ingestion, Alert management, Calibration
- **Services**: SensorDataService, AlertService, DeviceManagementService, MQTTService
- **Permissions**: View live data, Manage sensors based on role
- **Dependencies**: django-channels (WebSockets), paho-mqtt, celery

### analytics
- **Purpose**: Data analysis, trend identification, and insight generation
- **Models**: Metric, KPI, TrendAnalysis, Insight, ReportTemplate, Dashboard
- **APIs**: Get metrics/KPIs, Create custom reports, Export data, Schedule reports
- **Services**: AnalyticsEngine, MetricsCalculator, TrendDetector, InsightGenerator
- **Permissions**: View based on role, Create reports based on permissions
- **Dependencies**: pandas, numpy, matplotlib, seaborn (for calculations)

### ai
- **Purpose**: Artificial intelligence services and model management
- **Models**: AIModel, ModelVersion, Prediction, TrainingJob, Recommendation, Anomaly
- **APIs**: Get predictions, Trigger recommendations, View anomalies, Manage models
- **Services**: PredictionService, RecommendationEngine, AnomalyDetector, ModelTrainer
- **Permissions**: Based on AI feature access roles
- **Dependencies**: TensorFlow/PyTorch, scikit-learn, transformers, ONNX

### reports
- **Purpose**: Generate, schedule, and deliver reports in various formats
- **Models**: Report, ReportSchedule, ReportExport, ReportTemplate
- **APIs**: Generate report, Schedule report, Download/Email report, View report history
- **Services**: ReportGenerationService, ExportService (PDF/Excel/CSV), SchedulingService
- **Permissions**: Based on report type and user role
- **Dependencies**: ReportLab, WeasyPrint, pandas, openpyxl

### notifications
- **Purpose**: Handle all system notifications (email, SMS, push, in-app)
- **Models**: Notification, NotificationTemplate, NotificationPreference, NotificationLog
- **APIs**: Send notification, Get user notifications, Mark as read, Manage preferences
- **Services**: NotificationService, EmailService, SMSService, PushService, TemplateService
- **Permissions**: Users can only see/manage their own notifications
- **Dependencies**: Django core mail, twilio (for SMS), firebase/cloud messaging (for push)

### audit
- **Purpose**: Comprehensive audit logging and compliance tracking
- **Models**: AuditLog, DataChangeLog, AccessLog, ComplianceReport
- **APIs**: Get audit trails, Export compliance reports, Search/filter logs
- **Services**: AuditingService, ComplianceService, LogRetentionService
- **Permissions**: Admin/auditor roles only for most operations
- **Dependencies**: django-simple-history or custom audit implementation

## 5. Database Design

### Tables Overview

#### accounts_user
- PK: id (UUID)
- Important Fields: email (unique), username, first_name, last_name, is_active, date_joined, last_login, role (enum), institution_id (FK)
- Relationships: FK to accounts_profile, accounts_role, campus_institution

#### accounts_profile
- PK: id (UUID)
- FK: user_id (UUID) -> accounts_user.id
- Important Fields: phone_number, date_of_birth, address, avatar, bio
- Relationships: One-to-one with accounts_user

#### accounts_role
- PK: id (UUID)
- Important Fields: name (unique), description, permissions (JSONField)
- Relationships: M2M with accounts_user through accounts_user_roles

#### core_systemconfiguration
- PK: id (UUID)
- Important Fields: key (unique), value (JSON), description, is_public, updated_at
- Relationships: None (standalone configuration)

#### campus_institution
- PK: id (UUID)
- Important Fields: name (unique), domain, established_date, website, logo, timezone
- Relationships: One-to-many with campus_campus

#### campus_campus
- PK: id (UUID)
- FK: institution_id (UUID) -> campus_institution.id
- Important Fields: name, code (unique within institution), address, latitude, longitude, established_date
- Relationships: FK to campus_institution, One-to-many with campus_building

## 7. Authentication Flow

### JWT Flow
1. **Login**: User sends credentials to `/api/v1/auth/login/`
2. **Token Generation**: Backend validates credentials, generates:
   - Access Token (short-lived: 15 minutes)
   - Refresh Token (long-lived: 7 days)
3. **Token Storage**: Frontend stores tokens in secure HTTP-only cookies or secure localStorage
4. **Authenticated Requests**: Frontend sends Access Token in Authorization header: `Bearer <token>`
5. **Token Validation**: Backend verifies token signature, expiration, and claims
6. **Token Refresh**: When access token expires, frontend uses refresh token to get new pair
7. **Logout**: Backend blacklists refresh token, frontend clears stored tokens

### Refresh Tokens
- Stored in database with expiration and JWT ID (jti) for tracking
- Rotated on each use for security (refresh token rotation)
- Blacklisted immediately upon logout or suspicious activity
- HTTP-only, secure cookies to prevent XSS theft
- Limited to specific IP/user-agent combinations for additional security

### RBAC (Role-Based Access Control)
- **Roles**: SuperAdmin, InstitutionAdmin, CampusAdmin, BuildingManager, Faculty, Staff, Student, Auditor, Guest
- **Permissions**: Granular permissions assigned to roles (view, create, edit, delete, approve, export)
- **Role Assignment**: Users can have multiple roles, context-specific (per institution/campus)
- **Permission Checking**: Middleware checks user roles/permissions against endpoint requirements
- **Dynamic Roles**: Custom roles可 be created by admins with specific permission sets

### Permissions System
- **Authentication**: `IsAuthenticated` - user must be logged in
- **Ownership**: `IsOwner` - user owns the resource (based on foreign keys)
- **Institution Access**: `IsInstitutionMember` - user belongs to same institution
- **Campus Access**: `IsCampusMember` - user belongs to same campus
- **Role-Based**: `HasRole(role_name)` - user has specific role
- **Permission-Based**: `HasPermission(permission_codename)` - user has specific permission
- **Object-Level**: Custom permissions checking specific object attributes

### User Roles
1. **SuperAdmin**: Full system access across all institutions
2. **InstitutionAdmin**: Full access to their institution's data
3. **CampusAdmin**: Full access to their campus's data
4. **BuildingManager**: Manage buildings, floors, rooms under their responsibility
5. **Faculty**: View and report on their assigned spaces
6. **Staff**: Operational roles (maintenance, utilities, etc.)
7. **Student**: View personal and aggregated data, submit feedback
8. **Auditor**: Read-only access for compliance and auditing purposes
9. **Guest**: Limited public information access

## 8. AI Architecture

### Carbon Calculation Engine
- **Location**: `apps/carbon/services/CarbonCalculationService.py`
- **Components**: 
  - Emission factor manager (loads/update factors from external sources)
  - Scope 1, 2, 3 calculators (direct, indirect, value chain emissions)
  - Unit converter (standardizes measurements to CO2e)
  - Temporal adjustor (applies seasonal/weather corrections)
  - Validation engine (checks data quality and flags anomalies)
- **Inputs**: Resource consumption data, emission factors, metadata
- **Outputs**: CO2 equivalent values with calculation methodology and confidence scores
- **Caching**: Frequently used factors cached in Redis for performance

### Forecasting
- **Location**: `apps/ai/services/ForecastingService.py`
- **Models**: 
  - Time Series Models: Prophet, ARIMA, LSTM for consumption forecasting
  - Seasonal Decomposition: STL for trend/seasonality/residual analysis
  - External Regressors: Weather, occupancy, events as features
- **Training**: Automated retraining pipelines with performance monitoring
- **Prediction Horizon**: Short-term (hourly/daily), Medium-term (weekly/monthly), Long-term (yearly)
- **Outputs**: Point predictions with confidence intervals, scenario analysis

### Recommendation Engine
- **Location**: `apps/ai/services/RecommendationEngine.py`
- **Approaches**:
  - Collaborative Filtering: Similar institutions/campuses comparison
  - Content-Based: Feature-based similarity matching
  - Hybrid: Combines multiple approaches with weighted scoring
  - Rule-Based: Expert-defined rules for quick wins
  - Optimization: Linear programming for resource allocation
- **Inputs**: Historical data, benchmarks, constraints, goals
- **Outputs**: Ranked recommendations with estimated impact, cost, effort, timeline

### Anomaly Detection
- **Location**: `apps/ai/services/AnomalyDetector.py`
- **Techniques**:
  - Statistical: Z-score, IQR, Modified Z-score for univariate anomalies
  - Multivariate: Isolation Forest, One-Class SVM, Local Outlier Factor
  - Temporal: Seasonal Hybrid ESD (S-H-ESD), LSTM Autoencoders
  - Rule-Based: Threshold-based alerts for known problematic patterns
- **Features**: Consumption patterns, temporal patterns, correlations, external factors
- **Outputs**: Anomaly score, severity level, suggested investigation steps, confidence
- **Feedback Loop**: User feedback on anomalies improves model accuracy over time

### Model Management
- **Model Registry**: `apps/ai/models/` directory with versioned model files
- **Training Jobs**: Tracked in `ai_trainingjob` table with status, metrics, artifacts
- **Deployment**: Blue-green deployment strategy for zero-downtime updates
- **Monitoring**: Performance drift detection, data quality monitoring
- **Experiment Tracking**: MLflow or similar for experiment comparison

- **API Gateway**: Route requests to appropriate service (legacy or new)

- **Shared Kernel**: Common libraries for cross-cutting concerns

## 12. Risk Analysis

### Technical Risks

#### Data Volume and Performance Risk
- **Risk**: High-frequency sensor data causing database performance degradation
- **Mitigation**: 
  - Time-series database integration (InfluxDB/TimescaleDB) for sensor readings
  - Data aggregation and retention policies
  - Read replicas for analytical queries
  - Proper indexing and partitioning strategies
  - Caching layer (Redis) for frequently accessed data

#### AI Model Accuracy and Bias
- **Risk**: AI recommendations or predictions being inaccurate or biased
- **Mitigation**:
  - Continuous model validation against ground truth
  - Diverse training data collection across different institutions
  - Bias detection and mitigation techniques
  - Human-in-the-loop for critical recommendations
  - Model explainability tools (SHAP, LIME)

#### Security and Privacy Concerns
- **Risk**: Exposure of sensitive institutional or personal data
- **Mitigation**:
  - End-to-end encryption for data in transit and at rest
  - Regular security audits and penetration testing
  - Role-based access control with principle of least privilege
  - Data minimization and anonymization where appropriate
  - Compliance with GDPR, FERPA, and other relevant regulations

#### Integration Complexity with Legacy Systems
- **Risk**: Difficulty integrating with existing campus IT systems
- **Mitigation**:
  - API-first approach with well-documented REST endpoints
  - Adapter patterns for common protocols (BACnet, Modbus, etc.)
  - Middleware for data transformation and mapping
  - Pilot programs with volunteer institutions
  - Extensive testing with sandbox environments

#### Scalability Limitations
- **Risk**: Architecture not scaling to thousands of institutions
- **Mitigation**:
  - Microservices-ready design from the beginning
  - Stateless application design where possible
  - Horizontal scaling considerations in database design
  - Load testing at various scales during development
  - Cloud-native patterns and practices

### Operational Risks

#### Vendor Lock-in
- **Risk**: Dependence on specific cloud providers or technologies
- **Mitigation**:
  - Abstract service interfaces (storage, messaging, etc.)
  - Multi-cloud compatible design patterns
  - Open standards and formats where possible
  - Exit strategy planning from the beginning
  - Regular technology landscape reviews

#### Skill Gap and Team Expertise
- **Risk**: Team lacking expertise in Django, React, AI, or IoT domains
- **Mitigation**:
  - Comprehensive documentation and knowledge sharing
  - Training programs and mentoring
  - Hiring for complementary skills
  - Pair programming and code reviews
  - External consulting for specialized domains

#### Changing Requirements During Development
- **Risk**: Scope creep and changing stakeholder expectations
- **Mitigation**:
  - Agile development with regular sprint reviews
  - Clear definition of done and acceptance criteria
  - Stakeholder engagement throughout development
  - Feature flags for gradual rollout
  - Regular backlog grooming and prioritization

### Business Risks

#### Adoption Resistance
- **Risk**: Institutions reluctant to adopt new sustainability tracking systems
- **Mitigation**:
  - Clear ROI demonstration (cost savings, compliance benefits)
  - Phased implementation with quick wins
  - User-friendly interface and minimal training required
  - Success stories and case studies from pilot programs
  - Integration with existing workflows rather than replacement

#### Data Quality and Completeness
- **Risk**: Inconsistent or incomplete data from various sources
- **Mitigation**:
  - Data validation at point of entry
  - Automated data quality scoring and reporting
  - Imputation strategies for missing data
  - Data governance policies and procedures
  - User education on importance of accurate data entry

#### Technical Debt Accumulation
- **Risk**: Quick fixes leading to unmaintainable codebase
- **Mitigation**:
  - Definition of done includes code quality standards
  - Regular refactoring sprints
  - Automated testing (unit, integration, end-to-end)
  - Code reviews with quality gates
  - Technical debt tracking and prioritization
